# Console checklist: PSWaker diagnostic 01.03

Use this guide to validate the provided prototype for
[#13](https://github.com/Jcanotorr06/pswaker/issues/13). Allow about 40 minutes for
three ten-minute launches, installation and evidence retrieval. The package runs
synthetic graphics, audio, controller and runtime checks without game data.

**#13 stays open with `ready-for-human` until your observations and returned
evidence have been reviewed and pass.** This validates the exact package below.
#15 still owns the later renderer-reconciled stack's two clean builds and renewed
console gate after #14.

The required human evidence for #13 is your written observations plus matching
console logs and package identity. Photos/video are useful supporting evidence;
if none were taken, say so. Record unavailable timing or audio-output details as
`not recorded`. These omissions alone do not invalidate otherwise passing owner
observations and matching logs.

## 2. Prepare a cold cache and evidence folders

Fully close the diagnostic before changing its files. Its console directory is:

```text

```

- [ ] If the directory already exists, download a backup to your PC before testing.
- [ ] Preserve `preflight-state.txt` and existing logs. The state counter should

- [ ] After backing up, install the verified package using your existing console

  diagnostic evidence and persistent state when replacing an older version.
- [ ] For the first run only, use FTP to rename an existing `cache` directory to

- [ ] Create these folders on the PC for the evidence you will download:

  ```text

    run-2-warm/
    run-3-warm/
  ```

## 3. Run the same test on each launch

| Run | Cache before launch | Required duration |
| --- | --- | --- |
| 1 — cold | Empty, as prepared above | At least 600 displayed loop seconds |
| 2 — warm | Keep everything generated by run 1 | At least 600 displayed loop seconds |
| 3 — warm | Keep everything generated by run 2 | At least 600 displayed loop seconds |

Fully close the app and retrieve evidence between launches. Keep the same
installed package for all runs. If a run fails, follow section 5 and return its
evidence before retrying; additional attempts get their own folders.

### Start and inspect

- [ ] Record the run number, local date/time and time zone, and cache state.
- [ ] Launch the app. A shader-preparation panel may appear before the main scene.
  Record roughly how long startup takes.
- [ ] Confirm the panel says **Disc-free diagnostic** and shows build
  **`f89abcb363a45bfbe8cc`**. The retained word **Prototype** is expected.
- [ ] Check and record the following. If possible, take an early photo showing
  the scene and panel:

  | Observation | Expected result |
  | --- | --- |
  | Background and triangle | White background with a visible red/green/blue triangle |
  | Preview in the panel | Purple swatch |
  | Text | Readable panel; timer and frame count advance |
  | Size | Internal `1280x720`; surface `1920x1080` |
  | Counters | Failures `0`; audio errors `0`; checks increase about every five seconds |
  | Sound | Quiet, steady 440 Hz tone through the selected audio output |

  Report missing elements, corruption, flicker, audio gaps or distortion. The
  internal target size and output surface size describe different things.

### Exercise the controller once during every run

- [ ] With the pad connected, press ordinary face/directional buttons and vary
  L2/R2. Confirm the displayed button mask and trigger values respond. Save
  **Options** for the end of the test.
- [ ] Hold a direction or ordinary button, then disconnect/power off the controller
  using your normal method. Confirm `Pad 0` and neutral displayed button/trigger
  values. Record any stuck input or unexpected behavior.
- [ ] Reconnect. Confirm `Pad 1` and that disconnect/reconnect counters increased.
- [ ] Release Cross, then deliberately press **Cross / ×**. The
  **Waiting for Cross after reconnect** message should clear. The scene/timer
  can continue while this prompt is present; the prompt checks deliberate resume.
- [ ] Note any change to sound, graphics or responsiveness during this sequence.

### Finish the ten-minute loop and close

- [ ] Let the app reach at least **600 displayed seconds**, excluding startup and
  preparation. Watch/listen throughout for crashes, freezes, corruption and audio
  interruptions. Record any time spent in console menus or intentional interruption.
- [ ] Confirm the panel says **Loop complete. Retrieve logs; owner observation
  still required.** Expected failures and audio errors remain **0**. Around 120
  check cycles is typical; report the actual count rather than changing it.
- [ ] Record the final build, timer, counters and sizes. An end-of-run photo and
  a short video with sound are helpful if available; otherwise report that none
  were taken. State separately whether the tone stayed continuous for the full
  run; a short clip cannot establish that by itself.
- [ ] Release, then press **Options** to finish. The app performs shutdown checks;
  record whether it returns normally to the console shell. If you need the shell's
  Close Application action, record that intervention.
- [ ] Download the files in section 4 **before launching again**.
- [ ] On the next launch, retain the cache and state. Compare the downloaded
  `preflight-state.txt` values: each launch that reaches the state update should
  increment the prior value by one. Label recorded counters as before-run or
  after-run values. Record extra attempts as well.

Exiting before 600 seconds or skipping disconnect/reconnect/resume produces
failed end-of-run checks. Preserve such a run as an incomplete/failed attempt.

## 4. Retrieve and return the evidence

After **each** close, copy these files from
`/data/pswaker-diagnostic-prototype/` into that run's PC folder:

| File | What it provides |
| --- | --- |
| `diagnostic.log` | Build/launch identity, graphics/input/audio/resource checks and shutdown stages |
| `runtime-preflight.log` | Constructors, TLS, synchronization and file replacement results |
| `preflight-state.txt` | Persistent launch counter |
| `platform.log` | Current native platform, graphics and display output |
| `platform.prev.log`, if present | Previous rotated platform output |

- [ ] Keep complete file copies. `diagnostic.log` and `runtime-preflight.log`
  append launches, including older versions; leave those blocks intact. The
  reviewer will match the current `BEGIN build=...`, `RUN launch=...` and runtime
  launch counter. Platform logs rotate, so retrieving them after every run matters.
- [ ] Record a directory listing of `cache/` before run 1 and after each run
  (filenames, sizes and modification times, using your FTP client). Report an empty
  cache as empty. Keep the cache files on the console between warm runs; uploading
  their binary contents is not required initially.
- [ ] If any requested file is missing, name it in `report.md`. Missing logs after
  a crash are still useful information; a folder's absence does not prove no code ran.
- [ ] Include any photos/video taken in the corresponding run folder. If none
  were taken, state that in the report.
- [ ] Fill in the report template below. Zip `report.md` and the three run folders
  and send them back in this conversation or attach them to #13. Keep the original
  backup locally. The PKG, ELF, game files, credentials, keys, console account IDs
  and private network details are not needed in the evidence upload; crop/redact
  private information from shared copies if it appears.

The reviewer will inspect the logs for successful pipeline preparation, allocated
1280x720 EFB targets, exact-white EFB/offscreen comparisons, purple readbacks,
runtime/input/audio/persistence checks, and bounded resource observations. You do
not need to interpret memory counters yourself. Expected shutdown evidence includes
`PASS GPU-queue-drained`, `STAGE Aurora-shutdown-complete`, and `END ... failures=0`.
The displayed zero count before Options alone does not establish shutdown success.

## 5. If startup, a test or shutdown fails

1. Record the run/cache state, displayed build if visible, elapsed time, last
   visible scene/counters, sound behavior and exact console error code. Photograph
   the error or capture the failure if possible.
2. If the app hangs, record how long you waited and use the normal console close
   action if available. Record any forced close or reboot needed to recover.
3. Retrieve the same files **before another attempt**. Preserve partial logs,
   `FAIL` lines and warnings. If relevant runtime logs were created under
   `/data/DolphinPS4/`, include those or report the available filenames.
4. Keep the failing run separate. Report the failure before reinstalling, clearing
   the cache again or changing the environment; these actions affect reproduction.

A short failed attempt is useful evidence. It does not need to run for ten minutes.
Retain graphics/device messages even if they appear during shutdown: their timing
must be reviewed. These last-stage logs are not guaranteed crash dumps.
